# Production architecture

The Vite browser uses relative /api paths. Serve the Node application and API at one canonical HTTPS origin, with an authorized reverse proxy preserving the real Host. Never trust an arbitrary forwarded Host. Run an approved Node 22 application service with a private endpoint to a patched hosted PostgreSQL instance. Apply migrations with a distinct migration operator, then verify AUTH_DATABASE_URL and DATABASE_URL are least-privilege roles with authenticated TLS and forced RLS. Set environment values server-side. Restrict client address interpretation and rate limit at the trusted ingress.

PrivateStorage now uses an EvidenceObjects adapter. Default is the existing restricted disk directory. For durable Supabase use a dedicated private bucket, no anonymous/publishable access, an operator-controlled project, and server-side PRIVATE_OBJECT_ORIGIN, PRIVATE_OBJECT_BUCKET and PRIVATE_OBJECT_KEY. PRIVATE_STORAGE_DIRECTORY remains required by validation and designates the disk path only in disk mode. The adapter sends encrypted, bounded envelopes, prohibits overwrites, and limits object IDs to random hex. Client downloads still use short-lived ReeKlaim links scoped to the user and session, with authorization rechecked and integrity verified before decryption. The browser never receives the storage credential or object endpoint. The adapter supports provider cleanup of an uncommitted upload; application-governed deletion and retention automation still need an operating policy.

Do not switch an existing database to a different storage backend without exporting every referenced encrypted object under its existing key, verifying per-object integrity, rehearsing on a restore copy and backing up both stores and keys. Back up ciphertext and its database references consistently. Restore into a private test environment and verify a scoped download and unauthorized denial before any cutover. No migration checksum changed in Phase 9B.

Vercel static hosting cannot mount Vite's local middleware. Proposed release topology is Vercel frontend with reviewed same-origin routing to the Node service, or an independently tested Vercel Node function adaptation. The latter must prove request-size/timeout limits, session cookie behavior, raw uploads, application headers and database pool behavior. Ephemeral function disk is unsuitable. Actual integration, hosted verification and rollout remain open.
